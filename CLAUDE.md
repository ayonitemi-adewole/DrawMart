# DrawMart: notes for Claude Code

Ticket-draw marketplace for Lagos. React 19 + TypeScript + Tailwind v4 + Vite, React Router, TanStack Query. Backend not chosen yet; the app runs on an in-browser mock.

## Commands
- `npm run dev`, `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`
- Run `npm run typecheck && npm test && npm run lint` before committing.

## Rules of the codebase
- **Money is integer kobo** everywhere (`Kobo` type). Format only at the edge with `formatNaira`. Never use floats for money.
- **Business rules live in `src/domain/`** as pure functions with tests. Pages must not re-implement them; import from `domain/rules.ts`, `domain/fees.ts`, `domain/draw.ts`.
- **Pages talk only to `DrawMartApi`** through the hooks in `src/api/hooks.ts`. Don't import `mock.ts` from pages.
- When adding an API method: add it to `src/api/types.ts`, implement it in `mock.ts` (test in `mock.test.ts`) and in `supabase.ts`, then add a hook.
- Supabase: clients only read tables (RLS); every write is a `security definer` function in a new migration under `supabase/migrations/`, granted to `authenticated`. Never edit a pushed migration. Mirror `src/domain` rules in SQL and cover them in `supabase/tests/db.test.ts` (PGlite, runs in `npm test`).
- Secrets (draw seeds) live in the `private` schema, which the API doesn't expose. Never use the Supabase secret key in the app.
- `draw_results.winner_user_id` is not readable by clients: select named columns, never `*`, and derive "you won" from the user's own tickets.
- Buyer (`/`), store (`/store`), admin (`/admin`) and delivery (`/delivery`) are separate apps that never link to each other; everyone enters through `/login`, which sends each account to its own app (`src/lib/apps.ts`). Each account has exactly one `role` (`profiles.role`, `AuthSession.role`); only buyers hold tickets or wallet money (enforced in SQL). Use `useAccess().role` and guard routes with `<RequireSignIn role=…>`; buyer browsing stays public. The mock has demo accounts (`src/api/demoAccounts.ts`) so it goes through sign-in too.
- Wallet balances are derived from the append-only ledger; never store a balance. Show a buyer's balance with `useBalanceText` (`src/lib/balanceVisibility.ts`), so the eye button on the wallet page hides it everywhere.
- The platform fee rate is never a seller input: it's `platformFeeBps(price)` (`src/domain/fees.ts` FEE_TIERS ↔ `public.fee_tiers`), set by the database when a listing is created. Don't show the percentage to sellers or add a fee control to their forms; show the naira fee and payout.
- Individual sellers are buyer accounts with `profiles.seller_id` (an `individual` merchant), created when an admin approves their `seller_applications` ID check. They sell regular products only, never raffles; `private.my_merchant_id()` covers both stores and individuals. NINs and ID photos (private `seller-ids` bucket) are only for the applicant and admins: never show them to buyers or stores. In the UI, `useHasShop()` gates shop data; the seller tools are `/sell` in the buyer app.
- Messages: `conversations` (one per buyer per product) and `messages` are readable only by that buyer and the seller's shop; writes go through `send_first_message` (creates the chat with its first message: there are never empty chats) / `send_message`. "Message seller" opens `/messages/new/:listingId`, which creates nothing until the buyer sends. A seller's call number lives in `merchant_contacts` and is only returned to buyers already chatting with them; never put it on listings or `merchants`. The UI polls (`useMessages`, `useConversations`); `src/pages/MessagesPage.tsx` serves both `/messages` and `/store/messages`.
- Seller insights: listing pages call `useRecordListingView` → `record_listing_view` (once per visitor per listing per Lagos day; never the seller's own). `listing_views` has no client grants; sellers only get aggregates from `merchant_metrics` (`getMerchantMetrics`). Summaries and tips live in `src/domain/metrics.ts`. Never expose who viewed.
- Boosts: `listings.boosted_until` drives "Sponsored" ordering (`withSponsoredFirst` in `src/domain/boosts.ts`). A boost starts only through `complete_boost` (service role, after Flutterwave's verify API) or `test_pay_boost` (test mode only). The Edge Functions settle both kinds of payment by tx_ref prefix: `DM-` top-ups, `BST-` boosts. Unlock rule, slot cap and packages live in `app_settings` / `boost_packages`.
- Shared pickups: draw items created together with `createListingBatch` share `listings.pickup_batch_id` and one caution fee (`pickupCautionFee`); each row shows the same amount, so count it once with `cautionFeesDue`. A trigger settles the fee across the pickup (`settlePickupFee`) whenever a member's status changes. No cars. Items saved before sending live in `saved_pickups` (`savePickupItems`, one per store, gone 7 days after the first save; edits don't extend it).
- Pinned locations: `AddressPicker` (live map, search, written address) is the only way to enter a delivery or pickup address. `Delivery.location` / `Handover.location` are required on new orders and bookings and must be inside Lagos (`locationError` in `src/domain/location.ts` ↔ `private.location_error`). Treat a pin as private as the address. Place lookups live in `src/lib/geocode.ts`; run them on submit or after the map settles (Nominatim's policy: one a second, no search-as-you-type). Leaflet loads on demand through `LocationMap.tsx`.
- Draw timing: selling the last ticket moves a raffle to `sold_out` (`close_ticket_sales`), storing `draw_at` and the closing ref (in `private.listing_seeds`), and notifies participants. `run_due_draws`, called by `process_deadlines`, runs the draw at `draw_at`, the deadline or 7 days after sell-out, whichever is sooner (`announcementDate`). Never reveal the seed or a result before then. A new listing status must be added to the listings policy, metrics and `ListingStatus`. Notifications are in `notifications` (`listNotifications`, wording in `NotificationsPage`). Everyone who held a ticket gets `WinCelebration` (a short reveal in `BuyerLayout`, then confetti and a pop-up for a winner) until `markWinCelebrated`; that's stored on the notification, not in the browser, so it shows once across devices. Any roll of ticket numbers must come from `revealFrames` (`src/domain/reveal.ts`): never the viewer's own tickets or their neighbours, no slowing to a stop, and no "so close" wording.
- Cart and checkout: `cart_items` holds regular products and won draws, never cars (`cartError`). `checkout` (all or nothing, credit first) makes one `orders` row per item, for a whole cart or one item (`/checkout?item=`). Won items have `is_prize` and cost nothing; `handled_by` is `drawmart` for them, except cars, so stores can't read a winner's details (only cars). Delivery needs a pin; `pickup` needs a `pickup_points` row and no address, so guard `delivery.address`. `buy_now` in SQL is only kept for older app versions.
- Account and addresses: `/account` holds profile (`updateProfile`, including `User.phone`) and settings. `saved_addresses` (`listAddresses`, `saveAddress`, `setDefaultAddress`, `deleteAddress`, rules in `src/domain/addresses.ts`) is readable only by its owner; checkout starts on `preferredAddress`. Orders copy the address rather than pointing at a saved one. On phones and tablets the bottom bar is Explore, Tickets, Results, Messages; Wallet, Sell and Account are in `NavMenu`.
- Saved items: `saved_listings` is readable only by its owner, not even admins; writes go through `save_listing` / `unsave_listing` (`canSaveListing` in `src/domain/saved.ts`). `SaveButton` is the heart; a signed-out tap goes to `/login` with `?save=` on the way back, which `SaveAfterSignIn` in `BuyerLayout` finishes. A `ListingCard` is a `div` holding a link and the heart, so keep buttons out of the link.
- Practice draw: `/practice` (`src/domain/practice.ts`, `PracticePage`) runs real draw maths in the browser only. It must never import from `@/api` (a test checks), give a prize or credit, or lose its "Practice: no money" label on any step.
- Saved-item alerts: every one goes through `private.alert_saved` (`savedAlertAllowed` in `src/domain/savedAlerts.ts`), which applies the switch (`push_preferences.saved_items`), once per saved item per kind, 3 a day and the weekly limit. Keep the wording plain facts. New kinds go in the notifications check constraint, `NotificationKind`, `NotificationsPage` and `push_for_notification`.
- Payouts: `public.payouts` has one line per sale, draw or caution fee (`payoutsFor` in `src/domain/payouts.ts` ↔ `private.sync_payouts`, run by triggers on `listings` and `orders`, which deliberately don't catch errors). Lines only move forward: waiting → due → paid. Only `mark_payouts_paid` (admin, with a reference) pays. Bank details are in `payout_accounts`, readable only by the seller and admins; only the `bank-account` Edge Function can write them, through `save_payout_account` (service role), with the name from Flutterwave. Never take an account name from the browser, and never show the full number to anyone else. Changing an account holds payouts for `PAYOUT_ACCOUNT_HOLD_HOURS`. Notifications about the shop as a whole have a null `listing_id`.
- Store notifications: `/store/notifications` is `NotificationsPage` with store wording; individual sellers get the same kinds on `/notifications`, linking to `/sell`. `store_*` kinds go through `private.notify_shop` (everyone with that `merchant_id` or `seller_id`) and carry no buyer details or winner. Reminders are `private.store_reminders` (`src/domain/storeNotifications.ts`), run by `process_deadlines`. The mock's inbox is `inbox()`, not `buyer()`, since a store's id is its shop's. Push switches are in `STORE_PUSH_CATEGORIES`.
- Push notifications: triggers call `private.queue_push` (which respects `push_preferences` and skips anyone with no device), a minute job calls the `send-push` Edge Function (`_shared/webpush.ts`), and `public/sw.js` shows them. New kinds go in a trigger and in `PUSH_CATEGORIES`. Nothing on a lock screen may include a delivery PIN, message text or an unannounced result. Triggers must catch their own errors, so a notification can never fail a draw or an order. Only call `subscribeThisDevice` from a tap. Sending is Supabase only; the mock keeps the records. The manifest is `standalone` so iPhones can get push.
- Winners wall: no client can read `winner_stories`, since it ties an account to a win. Everything goes through `winners_wall` (public), `my_winner_stories`, `pending_winner_stories`, `share_winner_story`, `withdraw_winner_story`, `review_winner_story`, which return named fields and never a user id. Show the first name only (`winnerStoryError`). Withdrawing deletes the name; `private.winner_consent_log` keeps the consent record. Bump `WINNER_CONSENT_VERSION` when `WINNER_CONSENT_TEXT` changes. Never add sample winners.
- Link previews: chat apps get `/listings/:id` from `api/listing-preview.mjs` (and `listing-preview-image.mjs`), sent there by the user-agent rule in `vercel.json`; `npm run dev` doesn't serve them. Files in `api/` are plain `.mjs` and can't import `src/`, so `api/_lib/preview.test.mjs` checks their money and share-sold formats against `src/domain`. Select named columns there, and only fetch photos from `/assets/` or our own storage (`photoUrl`).
- Product IDs: every listing has a permanent `productCode` (`PRD-7K3Q9X`, `src/domain/productCode.ts` ↔ `private.new_product_code`), set by a trigger when the row is created. `listings.id` stays the internal key; never show it. Show the code with `ProductId`, and put `ProductSearch` with `matchesProductSearch` / `listingMatchesSearch` on any new page listing several products.
- Deliveries: only a delivery account can mark an order delivered, through `confirm_delivery` with the buyer's 6-digit PIN (`src/domain/delivery.ts`). PINs live in `private.order_pins`, set by a trigger on `orders`, and reach only the buyer (`my_delivery_pins`, `OrderView.deliveryPin`); never send one to a store, admin or rider. Riders have no read access to `orders`: `delivery_jobs` returns named fields, with `dropOff` (buyer's name, address, pin, phone) only while they're carrying it. A wrong PIN returns a result rather than raising, because raising would undo the attempt count. `RouteMap` shows a fixed spot; `LocationMap` is for choosing one.
- Rejections: `rejectListing(id, reason, note)` (rules and wording in `src/domain/rejection.ts`) stores `listings.rejection_reason` / `rejection_note`, which only exist while rejected, so they never reach buyers. `resubmitListing` (`resubmit_listing`) sends the same row back to review, checked like a new listing, and clears them. It doesn't charge the caution fee again (`resentCautionFee`). "Fix and resend" opens `NewListing` / `NewProduct` with `fixing`, through `?fix=<id>`; the form disappears once the listing stops being rejected, so resend with `mutateAsync` rather than `mutate` callbacks.
- Listing actions: `ListingActions` (`src/pages/merchant/parts.tsx`) is on every store listing card; rules are in `src/domain/listingActions.ts`. `updateListing` and `withdrawListing` only work on `pending_review` before the pickup day (`canChangeInReview` ↔ `private.can_change_in_review`), and share their checks with `resubmitListing` through `private.set_listing_details`. `listings.revision` goes up on each change and `approveListing(id, revision)` refuses an older version. `withdrawn` is never public. Store accounts see the listing page at `/store/listings/:id` with buying off (`StoreViewNotice`). Forms open with `?fix=`, `?edit=` or `?copy=` (`listingFormFrom`). A mutation whose card can disappear on refresh must use `mutateAsync`: `mutate`'s own callbacks don't run once the component has gone.
- Stock: `listings.stock` (`src/domain/orders.ts`) is how many are left; `checkout` takes `quantity` per order (`maxOrderQuantity`, `quantityError` ↔ `private.order_quantity`) while the row is locked and sets `sold` at zero; `orders.price_kobo` and `fee_kobo` are for the whole order; and `for_sale` always has stock (a check constraint). So one listing has many orders: never assume one order per listing, except a prize (`orders_one_prize_per_listing`). Draws stay 1.
- Product controls: `ProductControls` on the product card, rules in `src/domain/productControls.ts`. `paused` is publicly readable (so orders, carts and chats keep working) but browse never asks for it. A big price change waits in `price_reviews`, which buyers can't read, and the listing keeps selling meanwhile; never send an on-sale product back to `pending_review`, because that hides it from buyers' orders and chats. `reviewed_price_kobo` is what the 20% is measured from. `checkout` takes `expectedTotalKobo` so a buyer is never charged a price they haven't seen.
- Cancelling orders: `cancelOrder` (`src/domain/orderCancel.ts` ↔ `public.cancel_order`), only while `paid`, never prizes. `private.cancel_order_now` does the work, for later features to reuse. How an order was paid is in `private.order_payments`, never shown to sellers. Refunds are ledger kind `order_refund`, not `refund`, which counts towards the weekly ticket limit. A cancelled order isn't a sale, so leave `status = 'cancelled'` out of anything counting orders.
- Delivery fees: `src/domain/deliveryFees.ts` ↔ `private.delivery_fee` and `checkout`. One fee per seller per checkout, on one of that seller's orders (`orders.delivery_fee_kobo`), never part of `price_kobo`, the payout or the platform fee. Paid in ledger kind `delivery_fee`, split in `private.order_payments`. Prices are in `delivery_prices` (one row per area pair, `area_a <= area_b`). A seller's `merchants.delivery_area` is public, so never store a pin there; the pin is in `shop_pickups` (`save_shop_pickup`, which sets the area), and `delivery_jobs` only gives it to the assigned rider before collecting or on a return. Cars and won items pay nothing. Include the fee in `expectedTotalKobo`.
- Confirming orders: `seller_confirm_order` (`src/domain/orderConfirm.ts`) needs a photo before `dispatch_order` will let an order go; `confirm_by` is set by a trigger on `orders`, and is null for won items and older orders. Time only counts from 9am to 10pm Lagos time (`addConfirmTime` ↔ `private.add_confirm_time`), so never add hours to it directly. `private.order_confirm_deadlines`, run by `process_deadlines`, reminds and then cancels with reason `not_confirmed`, which only the deadline can use, and pauses the product. The photo comes only from `CameraCapture` (live camera, no file picker) on a device `isPhoneOrTablet` accepts (`src/lib/device.ts`); that's a browser check, not a server one. Don't reuse the name `confirm_order`: it's the old buyer function that always refuses.
- Delivery checks: `src/domain/deliveryChecks.ts`. `pass_collection` / `fail_collection` before the rider leaves; `refuse_delivery` (needs the buyer's PIN; returns a result on a wrong one, like `confirm_delivery`) at the door; `complete_return` for the way back. `delivery_jobs` only gives `dropOff` once `collected_at` is set. `private.penalise_seller` adds a negative `charge` line to `payouts`, the buyer's credit, and suspends at 3 in 30 days (`merchants.suspended_at`, checked when listing, resuming and approving). Riders upload to `riders/<uid>/` in the photos bucket. Payout totals can include negative lines.
- Claims and returns: `src/domain/claims.ts`; `order_claims` has one row per order, and its return address and trip cost have no client grants, so select named columns. A sale line stays `waiting` until `delivered_at + 48h` with no claim in progress (`private.sync_payouts`, released by `private.release_sale_payouts`). Refunds happen in `pass_return_pickup`, when the rider has the item, and set `orders.refunded_at` while status stays `delivered`, so check that before counting a delivered order as a sale. Riders work returns through `return_jobs`.
- Listing checks: `src/domain/listingChecks.ts`. `listing_check_plan` issues a code and decides a spot check once (`private.listing_check_tickets`); `create_product` takes `p.check` and checks it in `private.check_listing_proof`. Videos and receipts are in the private `listing-checks` bucket under the shop's id, and `listing_checks` is readable only by the seller and admins: never show them to buyers. The video comes only from `VideoCapture` (live, no file picker). New individual sellers' limits are `private.check_new_seller_limits`, called wherever a product can go on sale or change price. The mock keeps proof files in memory only; its tests turn off the stores' rules (`listingChecks` option).
- Quick replies: `quick_replies` (shop-only reads; `save_quick_reply`, `delete_quick_reply`; rules in `src/domain/quickReplies.ts`). `QuickRepliesEditor` sits beside the inbox on `MessagesPage`; `MessageBox` shows `QuickReplyChips` for sellers. `Button` and `IconButton` are `type="button"` unless given `type="submit"`, and `Sheet` renders in a portal and keeps submits inside, so sheets can open inside forms.
- Seller help: `HelpPage` (`/store/help`, `/sell/help`) with answers in `src/domain/help.ts`, built from the rules' own constants (never the fee as a percentage). Support chats are `support_threads` / `support_messages` (one per shop; `send_support_message`, `reply_support`, `support_inbox`), separate from buyer conversations; `AdminSupportPage` answers. Reuses `MessageList` / `MessageBox` from `MessagesPage`.
- Store sign-up: `store_applications` (`src/domain/storeApplications.ts`, `StoreApplicationPage` at `/sell/business`, `AdminStoreApplicationsPage`). `approve_store_application` turns the applicant's own account into the store's (`private.store_account_blocker`: a buyer that hasn't bought or sold), so check it before adding other ways an account can change role. Documents use the private `seller-ids` bucket. The mock records converted accounts in `storeAccounts`, which sign-in and `getSession` read.
- Getting started: `GettingStarted` (`src/pages/merchant/`, rules in `src/domain/gettingStarted.ts`) on the store dashboard and `/sell`; computed from existing data, no tables. A new setup step goes in `StartStep`.
- Shop pages: `StorePage` at `/stores/:id` (and `/store/shop` for a store's own preview), edited with `ShopProfile`; rules in `src/domain/shopProfile.ts`. Clients can't read `merchants.cac_number`: select named columns (`MERCHANT_COLUMNS`), never `*`, and show `public_cac`, which is empty unless the store opted in. A new `merchants` column needs adding to that grant. The store's own or an admin gets the real number from `merchant_cac_number`.
- Reviews: `src/domain/reviews.ts` ↔ `public.submit_review` / `reply_to_review` / `set_review_hidden`. One per delivered order (never prizes) for 30 days, changeable until the seller replies; one reply. The public only reads them through `shop_reviews` (first name via `private.reviewer_name`, never `user_id`), and nothing shows until a shop has `REVIEWS_SHOWN_FROM`, except to the shop and admins. Hidden reviews don't count.
- Listings have a `kind`: `raffle` (tickets, escrow, caution fee) or `product` (fixed price, admin review only, no tickets/handover/caution fee). Anything `for_sale` is bought through `checkout` → an `Order` (paid → marked ready by the seller → taken by a rider → delivered, with the buyer's PIN). Price and checkout rules live in `src/domain/orders.ts` (`salePriceKobo`, `checkOrder`); products have `ticketCount` 0, so guard any ticket maths.
- Real top-ups go through `api.payments` (Flutterwave, Supabase only). Only `complete_deposit`, called by the Edge Functions in `supabase/functions/` after Flutterwave's verify API confirms the payment, may credit a deposit; never trust the browser's checkout result. The Flutterwave secret key lives only in Supabase secrets. Test keys while test mode is on.
- Draw seeds are secret until the draw runs. Never include `seed` in a listing response before `status === 'drawn'`.
- Design tokens are in `src/index.css` (`@theme`): use `bg-brand`, `text-muted`, `bg-ticket` etc., not raw hex values. Dark mode overrides the same tokens under `.dark`, so don't add `dark:` colour variants; use `text-on-brand` / `text-on-ticket` / `text-on-hero` for text on those fills.
- Reuse the UI kit before writing new markup: `components/ui.tsx` (Button/`buttonClass`, Card, Badge, Notice, Segmented, StatTile, EmptyState, Field/`inputCls`), `Sheet` for modals, `Countdown`, `TicketStub`.
- Touch targets ≥ 44px (`min-h-11`), real `<button>`/`<a>`/`<label>`, `aria-label` on icon-only buttons.
- Test data: sample listings live in `private.seed_demo_data()` and test accounts in `private.seed_test_accounts()` (migration `…_test_data_reset.sql`; `seed.sql` just calls them); `reset_test_data()` (admin, test mode) wipes and reseeds. Keep them in step with the mock's seed in `src/api/mock.ts`, `src/api/seedCatalog.ts` (↔ `private.seed_catalog()`) and `src/api/demoAccounts.ts`. The mock acts for whichever demo account is signed in (`buyer()`, `shopId()`), or buyer@ / the Ikeja store when nobody is.
- Test mode (`api.testMode`) shows demo controls (admin app, Live draws) and the test banner. Never let demo helpers run against a real backend.
